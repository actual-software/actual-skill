# Actual.ai Skill reference

The plugin works in Claude Code and Codex, in any repository with architecture rules committed in `.actual/rules/`, and stays silent in repositories without them.

## Governance

In Claude Code and Codex, the skill checks your agent's work against the architecture rules committed in `.actual/rules/`. When your agent leaves plan mode, its plan is checked before you see the approval dialog. At the end of every turn, its changes are checked too. A conflict goes back to the agent with the reason, and the turn continues until it's fixed.

A rule file in `.actual/rules/` may open with a YAML header (`adr_id`, a scope with `root` and `paths`, and so on). The header says which part of the repository an ADR governs, and the CLI reads it. The skill never parses it: it counts the files, hands them to the CLI, and relays what the CLI returns. A file with no header is still read in the original format. Reading headers needs `actual` 0.9.0 or later. On an older CLI, in a repository whose rules carry them, the checks and briefing stand down rather than act on the wrong scope, and the session start tells you to upgrade; no hook blocks, but the agent is asked to pause and offer the upgrade. Overrides are unchanged: `<doc-slug>::<rule-id>`.

Your agent is also briefed as it reads. When it opens a file covered by a rule, the rules governing that file are surfaced before it makes its first edit. A file it writes without reading first — usually a new one — is briefed when it writes it instead; that brief arrives with the result, after the write, so it is a reminder that can prompt a revision. Editing a file already briefed by its read adds nothing. Briefing is advisory: it never blocks anything.

Reads through the shell count too, and they are most of them. Measured across 212 local sessions, four in five file reads went through `cat`, `head`, `sed -n` or `grep` rather than the Read tool, and a hook never sees those. A Claude Code mod covers them, and where it loads it takes over the Read tool too, so both kinds of read go through one path with one context budget, one record of what has already been said, and one way of reporting it. Reading a file twice does not brief it twice, whichever way you read it. The mod needs Claude Code 2.1.287 or later; on 2.1.285 and 2.1.286 set `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` to load it. Without it the Read path still works on its own, without the cap or the report below.

Where the mod loads, briefing is capped so it cannot crowd out your agent's context: 48,000 characters per session by default, which is roughly two and a half times what a 40-file session was measured to use against a 425-rule repository. When the cap is reached your agent is told once, rather than briefing going quietly dead.

You can see briefing happen. Each read of a governed file reports one line to the transcript, the same shape every time — a state in caps at a fixed column, then what arrived, then the files:

```
actual-cli: ▌ BRIEFED    2 ADRs · 8 of 35 rules    tokens.ts
actual-cli: ▌ NO CHANGE  briefed earlier  tokens.ts
```

- **A governed file that briefs nothing says why**, rather than leaving you to guess: nothing new for it, the budget spent, or the CLI could not answer.
- **A read of files nothing governs reports nothing, once the CLI says so.** Most files in a repository are ungoverned, and a line on each would bury the reads that matter.
- **`/rules-brief` lists the session**, in the order it happened, those quiet reads included, with the reason beside each one: the last 40 of at most 200 records.

None of this governs: it never touches the Stop verdict, which is the implementation gate's. None of it costs your agent context either, because the model never reads these lines — they are not counted against the cap above. It does need a terminal or the desktop app: nothing is reported in `claude -p`, the SDK, the VS Code chat panel or a cloud session, though briefing itself still runs there.

After a turn that changed files, the end-of-turn check also asks your agent which of the session's ADRs it used, listing every ADR that briefing put in front of it. The agent answers once, by running `actual rules report-use` with a file and line for each ADR it names (or `--none`), and the CLI checks each line against the turn's changes. On a blocked turn the question rides on the block and asks for the answer once the block is fixed, and on a passed turn it adds one short continuation before the turn ends. A hook on the Bash tool lets that exact command run without a permission prompt, for this session and this repository only, and only where the repository has rules. Any command carrying more than its own flags (a pipe, `;`, `$(...)`, a redirect, a quote), or naming another repository or session, goes through Claude Code's usual permission flow. The answer and the lines it names stay on your machine. Telemetry gets which ADR each claim named and whether it checked out (and why not, when it didn't); the file path of a claim that checked out is sent only while you're signed in. The CLI asks only when that telemetry would be sent, so with telemetry off there's no question; debug mode still asks, because it logs what it would have sent. This needs an actual-cli with `rules report-use`; an older CLI never asks. Codex agents get the same question, but the plugin pre-approves the answer only in Claude Code, so in Codex it goes through Codex's usual approval.

Governance never gets in the way of unrelated work. Outside a repository with `.actual/rules/`, the checks do nothing. If the CLI is missing, outdated, or crashes, you get a message instead of a block. A rule that stays unresolved stops blocking after three denied rounds per session.

When a gate denies, you're asked what should happen, in Claude Code's own select dialog: **Revise the plan to conform** (the recommended choice, which sends the agent back to fix it), **Override all** the rules listed, which are the ones that gate is blocking, never a rule only the other gate is denying. After **Override**, a second question asks why: the check misread your change, the ADR doesn't apply here, the ADR is wrong, or the ADR is out of date. If the block is right and you're going ahead anyway, choose "Other" and type `accepted`; anything else you type there is kept as your reason. The override is then recorded with that code and the plan goes on to its approval (or, for the implementation gate, the turn ends). Anything you type under "Other" in the first question goes to the agent as your answer. If you dismiss either question, nothing is overridden and the agent relays the denial instead. You can also type `/actual-cli:override <rule-id|all> [code] [reason]` as a message at any time, which is also how to override just some of the rules. The code is one of `misread`, `not-here`, `adr-wrong`, `adr-outdated` or `accepted`, and both it and the reason are optional. With actual 0.14.0 or later, the CLI stores the code with the override and sends it to Actual. Words you type after a code stay on your machine. Words that don't start with one of the five codes are stored with the code `other`, and those may be sent too (signed-in runs only): cut to 280 characters, with anything that looks like a secret (a token, key, password, or long hex or base64 string) removed first, and shown only to your organization's admins. An older CLI keeps the code as part of the reason. If you'd rather the agent revise on its own without asking, turn off the "Governance: ask how to handle a denial" row under `/plugin`, or set `ACTUAL_OVERRIDE_DIALOG=off`; typing the command still works. Use the full name: Claude Code only registers plugin commands under the plugin's prefix, so a bare `/override` comes back as an unknown command.

Only you can override. The dialog's answer goes to the plugin, not to the agent, and the CLI refuses to record an in-session override from any process carrying Claude Code's `CLAUDECODE` marker. Every command the agent runs carries that marker, so the agent can't record one from its shell. Like the terminal check below, this raises the cost of an agent overriding itself rather than making it impossible. Each override is recorded with how it was issued (`session_dialog`, `session_prompt` or `terminal`) and which gate denied it. The dialog and in-session overrides need the mod (Claude Code 2.1.287 or later). Without it, or without a CLI that supports this, run `actual check-override --session <id> --rule <doc-slug>::<rule-id> --reason-code <code> --reason "<why>"` from a terminal instead. `--reason-code` takes the same five codes and needs actual 0.14.0 or later; a `--reason` without it is stored as `other`, and its text may be sent the same way (signed-in runs only). `--reason` is required by CLIs through v0.12.0.

For an agent nobody is watching, set `ACTUAL_UNATTENDED=on`, or turn on the "Governance: approve plans for an unattended agent" row under `/plugin`. Claude Code holds a plan that passes the check at its own approval dialog until someone answers, so an unattended agent would wait there indefinitely. With the switch on, the plugin answers that dialog for it. The plan check still runs first: a conflicting plan is denied and revised as before, and a plan it passes, or couldn't check, is approved, after which the session goes back to the permission mode it had before planning. The switch also turns the denial dialog off, so the agent revises on its own, and while it is on it approves plans in every repository, with rules or without. It is off by default. Leave it off wherever a person reviews plans, because it approves on their behalf. It uses the plan-approval hook Claude Code documents, measured on Claude Code 2.1.287 and 2.1.322, and `ACTUAL_PLAN_GATE=off` turns it off along with everything else.

Set `ACTUAL_PLAN_GATE=off` to turn governance off, `ACTUAL_RULES_BRIEF=off` to turn off briefing alone while the checks keep running, or `ACTUAL_RULES_DIR` to use a different rules directory. The briefing limits have their own variables — `ACTUAL_RULES_BRIEF_MAX_SESSION_CHARS` for the per-session cap and `ACTUAL_RULES_BRIEF_LIMIT`, `_RULES_PER_DECISION`, `_MAX_CHARS` and `_MIN_SCORE` for `actual rules brief`'s own limits — and the same settings appear as labelled rows under `/plugin`. `_MIN_SCORE` is worth knowing about if briefing feels noisy: a rule's score reflects how narrowly its `verify` path is written, so the useful floor differs per repository and there is no good default.

The hooks also stay silent inside the `claude` subprocesses `actual` itself spawns (marked with `ACTUAL_CLI_SUBPROCESS=1`), so the judge's own Stop hook can't rerun `impl-check` and recurse. Failures are silent by design, so if you need to see why briefing isn't appearing, set `ACTUAL_HOOK_DEBUG=1` and run `claude --debug`; it reports the rules directory, the CLI's exit status, why a reply was dropped, and how much context briefing has used. To see the telemetry the CLI sends, set `ACTUAL_TELEMETRY_DEBUG=1` before starting Claude Code: the plan and Stop checks add a line such as `telemetry debug: <session id> -> ~/.actualai/actual/telemetry-debug/<session id>.jsonl` to the message they show you, and that file lists every event the session's hooks queued, sent or held back. Where the mod loads, it briefs reads itself and shows no line yet, so on Claude Code 2.1.287 and later the line appears after the plan and Stop checks only; the read-time brief adds it only where the mod does not load. An actual-cli without debug mode prints no line, and the hooks show nothing extra. The session-end hook and `/actual-cli:override` write to the same file and show nothing. Run `bash hooks/tests/run.sh` to test the hooks locally, and `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude plugin test .` to test the mod; neither needs the network or a CLI install. Governance relies on Claude Code's and Codex's hooks, so it isn't available in ChatGPT, Cursor, or OpenCode.

## Governance in Codex

The Codex plugin runs the same hook scripts against the same CLI, so the rules, verdicts, round limit and overrides are the ones above. What differs follows from what Codex offers a hook:

- **The plan is checked when the Plan-mode turn ends.** Codex has no plan-approval step to hold back, so you see the first draft of the plan before it is checked.
- **A conflict ends the turn and asks you, in place of the dialog.** When either check blocks, the turn stops with a "Stopped" entry that lists the conflicts. The agent doesn't revise or undo anything first. To have it fix them, just reply, for example "revise to conform". The conflicts reach the agent with your message. To keep the work, type `actual override all <code>`, or a rule id in place of `all`, as your message. The codes are the dialog's: `misread`, `not-here`, `adr-wrong`, `adr-outdated` and `accepted`, and a reason can follow. The override is recorded, a "Stopped" entry confirms it, and your message never reaches the agent. For a run nobody is watching, such as `codex exec`, set `ACTUAL_UNATTENDED=on` or `ACTUAL_OVERRIDE_DIALOG=off`, and a conflict sends the agent straight back to revise instead.
- **Where the agent can show a picker, you choose from a list instead.** Codex's picker is the agent's own `request_user_input` tool. Plan mode always has it. Default mode has it only with Codex's experimental `default_mode_request_user_input` feature on, so start Codex with `codex --enable default_mode_request_user_input`, or set `default_mode_request_user_input = true` under `[features]` in its `config.toml`. When a check blocks, the agent then shows a picker: **Revise … to conform (Recommended)** or **Override**. After Override, a second picker asks why: the check misread your change, the ADR doesn't apply here, or the ADR is wrong. Choose "Other" and type `accepted` if the block is right and you're going ahead anyway, or `adr-outdated` if the ADR is out of date. If the picker goes unanswered (the agent doesn't show it, or you dismiss it), the turn ends with the typed choices above. `ACTUAL_CODEX_PICKER=off` always uses the typed choices.
- **Briefing comes from shell reads and patches.** Codex has no Read tool: the files a read-only shell command names (`cat`, `head`, `sed -n`, `grep`, `rg` and the like) are briefed after it runs, and the files a patch adds or updates are briefed before it applies. The per-session cap is the same 48,000 characters, kept by the CLI.
- **The session summary is a line at the end of a turn**, shown only when it changes, since Codex has no band above the prompt.
- **Each brief is a line, not a transcript row.** Codex shows what a hook adds to the agent's context to the agent only, so the brief itself never appears. Instead, a line such as `Actual AI: briefed 2 ADRs · 7 rules · src/auth/tokens.ts` names what each brief carried. The agent never sees it. A read that briefed nothing new shows nothing, and there is no `/rules-brief` pane. Set `ACTUAL_RULES_BRIEF_NOTICE=off` to drop the line and keep the briefing.
- **Settings are environment variables only.** Codex has no per-plugin settings, so the `ACTUAL_*` variables above are the only way to set them.
- **The override command is `actual override`, typed as a message.** Codex has no plugin commands, so there is no `/actual-cli:override`. An override can't come from the agent's own shell: the CLI refuses one from any process carrying Codex's `CODEX_THREAD_ID` or `CODEX_SESSION_ID`. `actual check-override` from a terminal outside Codex still works too.
- **Each release asks you to trust the hooks again** (see [the install steps](install.md#codex-plugin)).
- **Codex needs `actual` 0.15.0 or later.** On an older CLI the session start offers the upgrade and the checks stand down.

## Session summary

In Claude Code, a row above the prompt shows what Actual AI has done for your agent this session: how many of your repository's ADRs it added to the agent's context, and how many folders the agent worked in that no ADR covers. It reads `Actual AI: 3 of 12 ADRs added to context · 2 areas with no ADR`, or `Actual AI: no ADR covers the 3 areas you worked in` while no ADR has been added. The CLI writes the row and the plugin shows it as given, and `actual session summary --json` names the folders. It reads `0 of 12` from the start of the session and updates whenever a read or write adds a decision to the agent's context or reaches a file no ADR governs, so both counts move while the agent is still planning, and again after each of your agent's replies. Each update runs in the background, so nothing waits on it. After `/clear` it counts the new session. Claude Code's own surveys and other plugins share that band: the row steps aside while a survey is showing, and the `[-]` at its right collapses the band.

In Codex the same line appears at the end of a turn, when it has changed since it was last shown. `ACTUAL_RULES_BRIEF=off` turns it off there along with briefing.

It counts against the same rules directory as briefing, `ACTUAL_RULES_DIR` included, and shows nothing outside a repository with `.actual/rules/`, when the rules hold no decision, or when the CLI is missing or too old to write the row. `ACTUAL_PLAN_GATE=off` leaves it on. The same mod that briefs shell reads draws it, so it needs the same Claude Code: 2.1.287 or later, or 2.1.285 and 2.1.286 with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`. The band appears in the terminal and the desktop app, and not in VS Code or `claude -p`. Its tests run with the mod's: `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude plugin test .`.

Once briefing reaches its per-session cap, the count can include the ADRs of the one brief that didn't fit: the CLI records each brief before the mod checks it against the cap, and the mod holds that one back.

## Troubleshooting

When something fails, the skill diagnoses it for you. It knows every error the CLI can return and all five runners (`claude-cli`, `anthropic-api`, `openai-api`, `codex-cli`, `cursor-cli`), so it can find the cause and retry without you reading logs.
